The standards gap

TRACE v0.2 already binds policy, runtime, data class, tool transcripts, identity and signatures into a verifiable Trust Record. Its public specification also identifies action receipts as a future profile direction. The fellowship contribution should therefore be precise: formalize the authorization-to-action binding rather than claim TRACE lacks evidence or signatures.

“Given a valid authorization, can an independent verifier prove that the executed action matched exactly what was authorized — and reject replay, tampering, expiry and identity mismatch?”
01 · ALREADY EXISTS

TRACE evidence foundation

TRACE v0.2 defines a signed Trust Record covering policy, runtime, model, data class, tool transcript, delegation and verification-related claims.

02 · CONTRIBUTION

Authorization semantics

Define a normative authorization object and verification algorithm that binds an authorized action/content to the corresponding TRACE execution evidence.

03 · OUTCOME

Independent verification

Give enterprises, auditors and standards implementers a deterministic way to answer whether execution was within the authorization that governed it.

The proposal

A deliberately narrow extension to the TRACE evidence model: define authorization semantics, prove the security properties, and demonstrate interoperable verification.

The proposed bridge

TRACE answers what ran, where, under which policy, and what tools were invoked. The proposed authorization layer adds the normative question: what was this execution actually authorized to do?

This is complementary to TRACE rather than a replacement for its attestation, evidence, hardware-rooted trust, or conformance model.

RFC 002 · Formal verification

Month 2–4: turn the proposed authorization semantics into machine-checkable security properties that complement TRACE's existing verification model.

PROPERTY 01

No-replay

An authorization carrying nonce N cannot be successfully consumed twice.

PROPERTY 02

No-tamper

Authorization bound to content hash C cannot authorize content C′ where C′ ≠ C.

PROPERTY 03

No-expiry-bypass

An authorization expiring at T cannot verify successfully at T′ > T.

PROPERTY 04

Deterministic rejection

Every verification failure maps to a named, deterministic rejection reason.

PROPERTY 05

Signature binding

An authorization signed by key K cannot be verified using a different key K′.

FORMAL MODEL

TLA+ state machine

Model lifecycle, verification and consumption states; peer-review the machine-checked properties.

Verification surface

AuthorizationRecord │ ├── signature valid? ├── policyDigest matches? ├── contentHash matches? ├── issuedAt / expiresAt valid? ├── nonce unused? └── verification outcome = named result │ ▼ EXECUTE / REJECT

Success: peer-reviewed TLA+ model · 50+ property tests · published conformance evidence · independent implementations agree on outcomes.

What stays out

The contribution is stronger because it does not attempt to solve every adjacent problem.

In scope

  • TRACE AuthorizationRecord specification
  • Formal security properties and proofs
  • Reference implementation
  • TRACE v0.3 authorization layer

Not required for this contribution

  • A full AGT policy → authorization mapping framework
  • A new confidential-compute architecture
  • Policy-to-authorization developer tooling
  • A broad product or commercialization program

These can be discussed with the community where they materially affect interoperability or the TRACE roadmap.
